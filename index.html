01 / ESGI Paris — 2024-2025
Speech-to-Text Temps Réel & Détection de Speakers
Développement d'un modèle Speech-to-Text français from scratch basé sur CNN, RNN et Self-Attention — déployé sur GCP avec GKE, architecture microservices Kafka/FastAPI/React.
+
Contexte & Problème

Les solutions de transcription existantes (Whisper, Google STT) ne gèrent pas bien le français conversationnel et ne distinguent pas les interlocuteurs dans une réunion. L'objectif était de construire un système end-to-end capable de transcrire en temps réel, d'identifier qui parle, et de générer automatiquement un compte rendu structuré.

Architecture
▶ Micro (audio) → Kafka topic
▶ FastAPI consumer → modèle CNN/RNN/Attention
▶ Speaker diarization → identification des locuteurs
▶ OpenAI API → résumé & compte rendu
▶ React frontend → affichage temps réel
▶ GKE (Kubernetes) → déploiement scalable
Challenges rencontrés
  • Latence temps réel : le modèle devait transcrire sous 500ms — résolu par chunking audio optimisé et inférence asynchrone via FastAPI.
  • Qualité du modèle français : peu de données labellisées en français — entraînement sur corpus mixte + data augmentation (bruit, vitesse).
  • Diarization : séparer les voix en temps réel est complexe — architecture CNN pour extraire les embeddings vocaux et clustering dynamique.
  • Scalabilité : Kafka pour découpler la capture audio du traitement, GKE pour autoscaler selon la charge.
Résultats
  • Transcription temps réel fonctionnelle avec latence < 1s
  • Détection multi-speakers opérationnelle
  • Compte rendu automatique généré via GPT-4
  • Architecture microservices déployée sur GKE avec CI/CD complet

02 / ESGI Paris — 2024-2025
Prédiction Météorologique Temps Réel
Pipeline streaming sur données HD Rain avec comparaison LSTM vs ARIMA pour prévision courte durée.
+
Contexte & Problème

Les données météo HD Rain (haute définition) arrivent en flux continu. L'enjeu était de construire un pipeline capable d'ingérer ces données en temps réel, de les traiter, et de prédire les précipitations à courte échéance (<1h). Le défi principal : choisir entre un modèle statistique classique (ARIMA) et un modèle Deep Learning (LSTM) selon les contraintes de latence et de précision.

Architecture
▶ Données HD Rain → Kafka producer
▶ Spark Streaming → ingestion & preprocessing
▶ Feature engineering → séries temporelles
▶ LSTM (PyTorch) vs ARIMA → prédiction
▶ Évaluation comparative → MAE, RMSE
Challenges rencontrés
  • Données irrégulières : les flux HD Rain ont des gaps et des valeurs aberrantes — pipeline de nettoyage temps réel dans Spark.
  • Stationnarité ARIMA : les séries temporelles météo ne sont pas stationnaires — différenciation et tests ADF intégrés.
  • LSTM sur séquences longues : gestion du vanishing gradient — architecture bidirectionnelle avec dropout.
  • Comparaison équitable : même fenêtre temporelle et mêmes métriques pour les deux modèles.
Résultats & Enseignements
  • LSTM surpasse ARIMA sur les patterns non-linéaires (précipitations intenses)
  • ARIMA reste compétitif pour les tendances douces avec moins de ressources
  • Pipeline Kafka/Spark Streaming opérationnel en temps réel
  • Conclusion : choix du modèle selon le profil des données, pas de solution universelle

03 / ESGI Paris — 2024-2025
Prédiction de l'Affluence des Vélos à Chicago
Préparation et transformation de données historiques sur Azure Databricks — modèles XGBoost/Random Forest, pipelines Kedro, suivi MLflow, déploiement API Docker.
+
Contexte & Problème

La ville de Chicago veut optimiser la gestion de ses pistes cyclables et stations de vélos en libre-service. Le projet consistait à prédire le nombre de passages de vélos à différents points de la ville selon l'heure, le jour, la météo et les données historiques — pour anticiper la demande et optimiser la redistribution des vélos.

Architecture MLOps
▶ Données historiques → Azure Databricks
▶ Feature engineering → variables temporelles, météo
▶ Kedro pipeline → reproductibilité & scalabilité
▶ XGBoost / Random Forest → entraînement
▶ MLflow → tracking des expériences
▶ Docker API → déploiement du meilleur modèle
Challenges rencontrés
  • Données manquantes : stations hors service, comptages nuls — stratégie d'imputation et flagging des anomalies.
  • Features temporelles : capturer la saisonnalité (jour/nuit, weekend, saison) nécessite un encoding soigné.
  • Reproductibilité : structuration avec Kedro pour que chaque run soit traçable et reproductible.
  • Sélection du modèle : 30+ expériences trackées via MLflow pour choisir les meilleurs hyperparamètres.
Résultats
  • XGBoost obtient les meilleures performances sur ce dataset tabulaire structuré
  • Pipeline Kedro entièrement reproductible et documenté
  • 30+ expériences MLflow comparées systématiquement
  • Modèle final déployé comme API REST containerisée Docker, prête pour la prod

04 / Projet Personnel — 2025
Assistant IA d'Analyse de Documents Juridiques
Pipeline RAG + GraphRAG avec observabilité LangSmith — extraction de clauses, raisonnement sur graphe de contrats et évaluation continue des réponses LLM.
+
Contexte & Problème

Les équipes juridiques passent des heures à analyser des contrats volumineux pour identifier des clauses spécifiques, des dépendances entre parties ou des risques contractuels. L'objectif était de construire un assistant capable de répondre à des questions complexes sur un corpus de documents juridiques, en combinant recherche vectorielle et raisonnement sur graphe de connaissances.

Architecture
▶ PDF contrats → parsing & chunking sémantique
▶ Qdrant → index vectoriel des clauses
▶ Knowledge Graph → entités (parties, clauses, dates, obligations)
▶ RAG hybride → retrieval dense + graphe
▶ LangGraph → orchestration multi-agents
▶ LangSmith → tracing, éval & monitoring LLM
Stack technique détaillé
  • RAG classique : chunking par section juridique, embeddings OpenAI, recherche hybride dense + sparse dans Qdrant avec reranking cross-encoder.
  • GraphRAG : extraction automatique d'entités (parties, obligations, échéances) via LLM → construction d'un knowledge graph → traversal pour répondre aux questions relationnelles ("quelles clauses lient A à B ?").
  • LangGraph : orchestration d'un agent multi-étapes — router entre RAG vectoriel et GraphRAG selon la nature de la question.
  • LangSmith : tracing de chaque run LLM (inputs, outputs, latence, coût), création d'un dataset d'évaluation, scoring automatique des réponses (faithfulness, relevance).
Challenges & Solutions
  • Chunking juridique : les clauses ne se découpent pas bien en chunks fixes — chunking par structure logique (articles, alinéas) plutôt que par token count.
  • Hallucinations sur contrats : critique en production — guardrails stricts + vérification des citations sources via LangSmith traces.
  • Routing RAG vs GraphRAG : questions factuelles → RAG vectoriel ; questions relationnelles → GraphRAG. Classifier LLM pour router automatiquement.
  • Évaluation continue : LangSmith utilisé pour construire un benchmark de 50 questions-réponses de référence et suivre la régression des performances à chaque itération.
Résultats
−70% temps d'analyse de contrats
0.87 F1-score sur dataset de référence
100% runs tracés via LangSmith
